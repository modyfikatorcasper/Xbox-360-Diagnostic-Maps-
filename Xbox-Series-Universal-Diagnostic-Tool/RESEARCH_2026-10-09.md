# Xbox Series Universal Diagnostic Tool — research 2026-10-09

Status: DEVELOPMENT / RESEARCH. Default rule: READ ONLY on original SSD/NOR.

## 1. Main finding: retail Series X/S can be monitored with PicoDurangoPOST

Public project: https://github.com/xboxoneresearch/PicoDurangoPOST
Companion GUI: https://github.com/xboxoneresearch/XboxPostcodeMonitor
Error database: https://github.com/xboxoneresearch/errorcodes

PicoDurangoPOST supports Xbox Series S/X through the AARDVARK connector. On Raspberry Pi Pico:
- GP0 / physical pin 1 = SDA -> AARDVARK pin 3
- GP1 / physical pin 2 = SCL -> AARDVARK pin 1
- GND -> GND

The Pico exposes captured POST data to the PC over USB serial (115200). XboxPostcodeMonitor can save raw + decoded logs and synchronizes the error database.

Important: this is NOT normal retail kernel UART. It is POST monitoring over the Southbridge I2C/AARDVARK path, then USB serial from Pico to PC. For a retail console this is currently the most practical external boot/failure trace.

Recommended first hardware test for the 84%/94% update-loop console: capture POST continuously from standby -> boot -> update -> reboot/shutdown and compare against a known-good Series X of the closest possible board revision.

## 2. Plain UART vs POST

Research project ASPECT2-PCB:
https://github.com/xboxoneresearch/ASPECT2-PCB

ASPECT2 documents:
- POST monitoring via I2C: working
- SPI flash reading: working; authors note it could also support SPI NOR on Series-family
- kernel UART: devkit exclusive
- JTAG Southbridge: devkit exclusive

Conclusion for retail hardware: do not make kernel UART the primary diagnostic path. Implement POST/AARDVARK first. UART can remain an experimental/devkit module.

## 3. Southbridge NOR / SBFS

Xbox One Research Wiki documents a separate Southbridge filesystem on Series-era consoles: SBFS.
https://xboxoneresearch.github.io/wiki/boot/southbridge-file-system/

Known SBFS details:
- magic: `SFBS`
- headers at absolute offsets `0x10000` and `0x11000`
- page size: `0x1000`
- max file count: 24

Known files include:
- `smcfw.bin` — SMC firmware
- `psp1sp.bin` — bootloaders, per-console
- `speaker.bin`
- `smcerr.log` — SMC error log, per-console
- `smc_d.cfg` — dynamic SMC configuration, per-console
- `certkeys.smc` — SMC boot capability certificate, per-console

This makes before/after NOR comparison highly valuable. The first files to track are `smcerr.log` and `smc_d.cfg`.

Public parser/extractor:
https://github.com/RetroTechCorner/sbfs-tool

`sbfs-tool` is experimental/WIP. For this project use extraction/read-only paths only. Do not modify sequence numbers or inject data into an original dump.

Community repair evidence also confirms that the small NOR on the Series X Southbridge board contains unique data and should be copied when replacing the entire SB board. Relevant threads:
- https://gbatemp.net/threads/xbox-series-x-testpoints-tp-readings.668894/
- https://www.tronicsfixforum.com/t/help-identify-smd-component-on-sb-board-xbox-series-x/14735/14

## 4. Series SSD raw XBFS region

Xbox Research documentation:
https://xboxoneresearch.github.io/wiki/boot/xbox-boot-file-system/

Series S/X use a dedicated logical XBFS area on internal NVMe:
- logical size `0x40000000` = 1 GiB
- Series header offsets: `0x0` and `0x18008000`
- documentation notes a Series-specific `0x6000` offset adjustment when calculating file locations

Interesting XBFS files include:
- `smcerr.log`
- `smc_d.cfg`
- `sp_s.cfg` — contains per-console/static SP data
- `os_d.cfg`
- `update.cfg`
- `update2.cfg`
- `recovery.dat`
- `system.xvd`
- `$sospf.xvd`

Public tools:
- https://github.com/RetroTechCorner/xbfs-tool
- https://github.com/emoose/xvdtool

`xbfs-tool` explicitly warns that modifying XBFS can brick the console. Our MVP must only inspect/extract from a raw image.

## 5. System Support / ODD update logs

The ODD firmware updater writes logs under:
`SystemSupport\oddfwupd\`

Historical Xbox Research documentation contains concrete failure strings/codes, e.g.:
- `FAILED to find ODD physical device`
- `GetOddPhysicalDevice failed`
- `ODDFW update failed`
- `80910002` for missing/not-found ODD path in documented cases
- `80910008` for drive authentication failures in documented cases
- pairing/firmware state is also recorded

Reference:
https://github.com/Randname666/xboxoneresearch-wiki/blob/master/optical-disc-drive.md

For every failed update attempt our tool should snapshot all `System Support`, preserve timestamps, index every log, and surface HRESULT/NTSTATUS/E-codes.

## 6. SSD compatibility / replacement: do NOT assume every NVMe works

Known physical format is M.2 2230 NVMe. Common original/known compatible families discussed by repair community include WD `CH SN530`, `CH SN560` and some Lite-On/SSSTC XA1 variants. `PC SN530` is not equivalent to `CH SN530`.

Series X|S uses Advanced Format 4Kn storage; Microsoft/DirectX engineering material explicitly describes Series X|S storage as 4Kn. Any imaging/restoration code must query logical/physical sector geometry and must not blindly assume 512-byte sectors.

Reference:
https://walbourn.github.io/advanced-format-drives-and-async-i-o/

Recent repair-community reports still show that generic 2230 NVMe replacement is unreliable and the original console-specific 1 GiB raw data remains critical. Treat exact SSD model/controller compatibility and the current console-specific raw image as separate requirements.

Do not use old `xboxonehdd` create/erase/rewrite scripts directly against an original Series SSD. They are useful as Xbox One partition-layout reference but destructive creation steps are outside the safe Series diagnostic workflow.

## 7. Best diagnostic workflow for the current 84% Applying / 94% Overall case

Create a single CASE ID and collect four synchronized evidence sources.

### BEFORE one controlled update attempt
1. Capture SSD identity, SMART/NVMe health, sector sizes and GPT.
2. Copy entire `System Support` read-only.
3. RAW image the 1 GiB Series XBFS region and SHA-256 it.
4. Dump the Southbridge SPI NOR twice and verify both dumps are identical.
5. Parse/extract SBFS from the verified NOR dump.
6. Connect PicoDurangoPOST and begin logging before power-on.

### RUN exactly one update attempt
Capture POST continuously through:
standby -> boot -> update -> 84% Applying / 94% Overall -> reboot/shutdown.

### AFTER
1. Copy `System Support` again.
2. Re-image 1 GiB XBFS.
3. Re-dump NOR twice and verify.
4. Extract SBFS again.
5. Stop/save POST log.

### COMPARE
- `System Support BEFORE vs AFTER`
- `XBFS BEFORE vs AFTER`
- `SBFS/NOR BEFORE vs AFTER`
- last POST sequence/codes before failure

If possible, repeat the same capture on a known-good Series X of the same/closest board revision.

The point is to stop guessing whether the fault is SSD, ODD, SB, SP, update state or another device. A 4-way correlation should show what changes immediately before the failure.

## 9. Safety rules

- Original SSD: READ ONLY by default.
- Original NOR: dump only until two identical reads are obtained.
- No automatic CHKDSK / repair / initialize / clean / GPT rewrite.
- No XBFS/SBFS injection in MVP.
- Every raw dump gets SHA-256 immediately.
- Every experimental write is performed only on a verified clone/donor after explicit operator confirmation.
